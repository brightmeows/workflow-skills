# 内容治理的维护理由

本文记录 `skills/doc-governance/SKILL.md` 的决策理由、证据与否决记录。技能正文是操作规则，本文是维护参考；dotfiles 的 `AGENTS.ref.md` 只留索引。

## 规则取舍

- dotfiles 的 `AGENTS.md` 本节按变更的四操作组织：内容变更只有增、改、废、炼四种操作；“只改一处”（唯一性）贯穿全部操作。条目对应：放对地方（增）、源头同步（改，废弃时连引用、文档与配置一起清除）、不留旧账（改、废）、三次才抽象（炼）。
- 理论根：Lehman 软件演化定律（软件持续变化；复杂性持续增加，除非主动做反向工作——“不留旧账”与 oxlint 棘轮对抗的正是它）；技术债的 Cunningham 原义（用不完整的理解写代码，欠下回头重构的义务——漂移是常态，偿还机制是纪律）；内容生命周期（创建、维护、归档、退役都是正常阶段，退役不是失败状态）。
- 检验后不进常驻规则的理论：Hyrum 定律（一切可观察行为都会被依赖——dotfiles 消费面小，改动前评估消费面即可）；Kent Beck 两段式（先让变更变容易，再做容易的变更——已由提交粒度的 type 拆分覆盖）。
- 放对地方的详细裁决：语义边界定为“跨实体即算”（超出单个代码实体的承载范围就升级；单模块内多文件的约定可写该模块的子 AGENTS.md）；where 指导航（东西在哪里），which 指选择（该用哪个）；覆盖范围只限开发用文档；保留“一般”语义的默认规则强度，没有写成硬性禁令。
- 外部证据：Atwood《Code Tells You How, Comments Tell You Why》（stackoverflow.blog 的评论最佳实践，引为权威）；docstring 惯例（描述对外契约，与行内注释分工）；
  AI Hero《A Complete Guide To AGENTS.md》（where/which 语义、monorepo 嵌套作用域、每层只放该作用域相关的信息）；wiki-update 规范（原地编辑，不追加日期段落）。

## 否决

- 把 README/docs 纳入四操作阶梯（面向使用者的文档与记录型文档不按开发内容治理，docs/ 维护记录可保留演进时间线）。
- 严格字面的“仅多模块协作才进子 AGENTS.md”（与范围最小化不自洽）。
- 在主文件写“导航信息易漂移”的警示（常驻预算不展开，记为维护信号）。

## 维护信号

- 代理在 README/docs 强行套用治理规则、或把使用者文档当开发文档写导航时，加强豁免句。
- 导航类信息频繁漂移（路径改名即失效）时，加“写入口与布局、别硬编码路径”。
- 与“只改一处”出现适用争议时，重议边界。
- 演进失守的实例（迁移半途而废、废弃漏清关联）再现时，把四操作升格为流程化技能。
