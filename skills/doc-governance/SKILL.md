# 内容治理

内容变更只有四种操作：增、改、废、炼。四种都挂在同一条线上——同一个事实只存在一处。

## 只改一处

配置、常量、版本号、文档表述，同一事实只在权威源头改，其他位置引用它或从它生成。

两处各写一份，早晚会分叉；分叉之后没人知道哪份是真的。判断权威源头的问法：这个值要改的时候，第一个该动的地方在哪。

## 增：放对地方

按信息的用途分层：

| 信息 | 放哪 |
| --- | --- |
| how，怎么做的 | 代码本身 |
| why，为什么这样做 | 代码旁边的行内注释 |
| what，这个类或模块或函数是什么 | 类、模块、函数注释 |
| 跨实体的导航与约定，在哪里、用哪个 | 开发用文档：根或子目录的 AGENTS.md、贡献者文档 |

开发用文档按覆盖范围选最小够用的层级：单模块内的约定写该模块的子 AGENTS.md，跨模块的才上升。

使用者文档与记录型文档不套这套。README 与 `docs/` 下的说明和记录可以保留演进时间线。

## 改：源头同步

动了权威源头，就同步所有下游产物：文档、生成物、副本、引用。

- 废弃时把引用、文档、配置一起清掉；留一半比不留更坏
- 产物过期就重新生成，不手动修补生成物，手改过的生成物下次生成就丢

## 废：不留旧账

内容只保留当前有效的状态：

- 更新时在原地重写，不追加带日期的更新段落
- 废弃时直接删掉，不留注释版，也不留“已废弃”标记
- 变更历史交给 git，文档不重复记录时间维度

例外是有组织的状态表，比如 ADR 的 superseded 状态、维护参考里的改判记录。它们本身就是当前状态的一部分。

## 炼：三次才抽象

同样的东西重复到第三次才提炼成共享的，在那之前容忍重复；提取时机的完整判据见 `abstraction-design` 的 Rule of Three。

- 碰巧相似不等于同一个事实：两个值现在相等但变更来源不同，就分开
- 不该合并的硬抽，会在下一次分叉时变成参数和条件分支

## 完成判据

- 每个事实只有一处权威表述，改行为只需要改那一处
- 没有留下指向已删内容的引用
- 生成物由源头重新生成，不是手改的
